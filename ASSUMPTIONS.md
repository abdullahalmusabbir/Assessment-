# Assumptions and Requirements Decisions

This document records assumptions and unresolved decisions for the
School Admission System. It is intended to make requirement gaps visible
rather than silently deciding them in code.

## 1. Admission Selection Policy: First-Come-First-Served vs Lottery

### Requirement discrepancy

The original assignment description indicates a first-come-first-served
admission process and says that admission is not based on a lottery. The
later custom project requirement asks for a lottery after successful
payment.

These are different admission policies and cannot both determine the
same seat allocation outcome.

### Current implementation direction

The custom workflow requested for this project is:

1.  A student applies to an eligible admission circular.
2.  The backend creates a Student ID and temporary Admission Hold.
3.  The student must complete payment before the hold expires.
4.  An unpaid and expired hold is released, and its associated temporary
    Student ID/application records are cleaned up according to the
    domain model.
5.  A successfully paid application remains eligible for the subsequent
    lottery.
6.  The lottery is generated by the backend and the result is persisted.

### Decision required

The project owner or evaluator must confirm which policy is
authoritative:

-   **Option A --- First-come-first-served:** allocate seats according
    to the approved timestamp/ordering rules. Do not run a lottery.
-   **Option B --- Lottery:** collect eligible paid applications and
    select students through the approved lottery rules.

Until this is confirmed, lottery-related code should be treated as
implementing the custom requested workflow, not as proof that it matches
the original assignment wording.

## 2. Role Identifiers

The frontend currently assumes these numeric role IDs:

    ID Role
  ---- ------------------
     1 Student
     2 Admission Office
     3 Admin

The backend enum/database values and JWT claims must use the same
mapping. If the backend uses different values, update the frontend role
mapping and authorization policies together.

## 3. Backend Project Layout

The backend is intended to remain a single ASP.NET Core Web API project
located at:

``` text
E:\.NET Project\school\backend\backend.csproj
```

Feature folders organize code within this project. Do not create one
independent `.csproj` for each feature or folder.

## 4. Database

The project is intended to use PostgreSQL. The actual connection string,
hosting provider, schema, migration history, and database availability
must be verified in the development environment.

Do not assume that `localhost:5432` is available. A hosted PostgreSQL
database may require a remote connection string and provider-specific
SSL settings.

## 5. Authentication

The frontend expects JWT-based authentication and uses API paths
configured in its API client. The actual backend route names, token
response shape, refresh-token behavior, and `/me` endpoint must be
verified against the implemented controllers.

Google login requires a configured Google OAuth client and server-side
token validation. A frontend Google button alone does not complete
Google authentication.

## 6. Frontend API Contract

Some frontend dashboard pages use conventional REST endpoint paths and
illustrative DTO field names. These names are not guaranteed to match
the backend.

Before integration is considered complete, verify: - Controller route
and HTTP verb - Request DTO names and validation - Response DTO
structure - Pagination/filtering contract - Role and ownership
authorization - Error response format

Do not change database entities solely to match a placeholder frontend
field. Align the API contract deliberately.

## 7. Payment Processing

A payment record or frontend payment status is not sufficient evidence
that a payment succeeded. The backend must verify the payment with the
selected payment provider or a trusted provider callback/webhook.

The following details require confirmation from the actual
implementation/provider: - Payment provider - Payment initiation
endpoint - Return/callback/webhook routes - Webhook signature
verification - Transaction reference format - Currency and amount
validation - Idempotency and duplicate callback handling - Hold expiry
duration and boundary behavior - Refund/cancellation behavior, if
applicable

## 8. Admission Hold and Student ID Lifecycle

The intended rule is that an unpaid expired hold should be released and
its related temporary Student ID should be removed if it has not become
a permanent/paid admission record.

The backend must enforce this atomically and respect foreign-key
relationships. Successful payment must prevent the expiry worker from
deleting the paid application or Student ID.

The exact entity relationships and deletion strategy must follow the
actual database model.

## 9. Lottery Rules

The following details must be explicitly approved and implemented on the
backend: - Which paid applications are eligible - Whether each student
can apply once or multiple times - Seat capacity per
class/shift/circular - Whether selection is random or follows another
ranking rule - How randomization is performed and audited - Whether a
lottery can be run more than once - How results are published - How
ties, cancellations, and vacant seats are handled

The frontend must never decide lottery winners.

## 10. Dashboard Statistics and Reports

Dashboard counts shown as placeholders must be replaced by
backend-calculated values. Reports should use server-side aggregation
and respect the requesting user's authorization scope.

## 11. Contact Form

If the frontend submits contact messages to a contact API, the backend
must provide the corresponding endpoint, validation, and
storage/delivery behavior. Otherwise, the frontend must be adjusted to
the actual supported contact mechanism.

## 12. Production Readiness

The presence of UI pages or API client methods does not establish
production readiness. Production readiness requires verified backend
authorization, secure secret management, payment verification, database
constraints, logging, error handling, backups, and end-to-end tests.
